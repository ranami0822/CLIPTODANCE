# 画像検索コラージュAI 設計方針(実装用)

Oct 31, 2026 · @Ryuuichiro

## 目標と前提(2026-10-31 決定)

- **目標**: 切り貼りが見えてよいコラージュ。ただし抽象画ではなく、全体として「ある程度、風景として成立している」もの。継ぎ目を完全に消す写実的な合成は目標にしない。
- **利用**: 個人利用。
- **権利**: 一旦後回し。ただし素材ごとの `source_url` / `license` の記録は残す(後から整理できるようにするため)。公開・共有、素材を外部サービスへ送る範囲の見直しなどの前に再検討する。

この前提から出てくる影響(以下は私の推測で、未決):

- 「自然さ」の意味は、「写真として本物に見える」ではなく「風景として破綻しない」(地平線・地面との接地・遠近とスケールの整合・重なり順)に寄せる。評価軸の「自然さ」(後述)の質問文もこれに合わせて直す必要がある。
- なじませは羽根ぼかし+アルファ合成を基本にし、ポアソン合成やPaint by Exampleは優先度を下げる(後続フェーズ)。
- 「地平線の位置」「地面の領域」を配置の入力に持つ必要があるかもしれない。背景に全面で使う素材の扱いも決める必要がある(未決)。

## 目的とスコープ

テキストの要望(任意で背景画像とスタイル名)から、検索した既存画像の切り抜きを配置・合成して1枚のコラージュを作るパイプラインを、Python(PyTorch)で実装する。生成モデルは学習せず、検索・判断・合成の部品を組み合わせる。

- 入力: 要望の文章。任意で、背景画像、素材プール名(洋画・日本画・イラストなど)、要素数の上限。
- 出力: 合成画像(PNG)と、採用した素材ID・変形パラメータ・各スコアを記録したJSONログ。
- 作らないもの: モデルの学習、実行時のWebスクレイピング、顔を含む写実合成(Paint by Exampleが顔を未対応とされるため)。
- 実行環境: GPUのある自分のPCかColabを本番とする。Claude側のクラウド環境はGPUなし(CPU 2コア、メモリ7GB)で、小規模な前処理と動作確認までを想定する。

## 基本方針

既存論文や実装の「挙動」(何をどの順でやるか)だけを倣い、中身の部品は現代のものに置き換える。

借りる挙動:

- Sketch2Photo(2009): スケッチと文字ラベルから、ネットで見つけた写真を縫い合わせる。不適切な検索結果をフィルタで除き、合成結果に数値の点を付けて最適な組み合わせを選び、最後に人が対話的に直す。
- Photo Clip Art(2007): 物体を加工して合わせるのではなく、向き・光・解像度が合う物体をライブラリから検索して選ぶ。
- CLIP-CLOP(2022): 人が素材(パッチ)のライブラリを用意し、評価役(CLIP)が構図を採点して最適化する。人が場を手で直せる余地を残す。

置き換え:

| 論文・既存実装の要素 | 現代版の部品 |
| --- | --- |
| 手描きスケッチとラベル(配置の指定) | Clairicが文章から物体ごとの位置・大きさ・回転と確信度を出す |
| ネット画像検索 | 事前に索引化した素材プールをCLIP系埋め込みで検索 |
| 不適切画像の除外フィルタ | SAMのマスク特徴量で足切り + Clefの属性判定(はい/いいえ・選択・採点) |
| 顧著性とGrabCutによる切り出し | SAM |
| 継ぎ目のない合成 | 縁のぼかしとポアソン合成(OpenCV)。写実プールではPaint by Exampleを任意で追加 |
| 合成結果の点数と最適な組み合わせの探索 | CLIPの一致度 + Clefの自然さスコア + 素材間の相性。上位候補での探索 |
| 対話的な修正 | 後続フェーズ。「この部品だけ差し替え」のUI |

設計の原則(案): 判断(Clef/Clairic)と画素処理(SAM/OpenCV)を分離し、判断側はadapter経由にして、ローカルCLIPや他のモデルに差し替えられるようにする。

## 素材プールと事前処理

素材は実行時に集めず、事前に集めて索引化する(権利管理と呼び出し費用を抑えるため)。

プールの方針:

- スタイル別(洋画・日本画・イラスト・写真など)に分け、コラージュ1作品の中では原則同じプールから選ぶ。光や質感のばらつきが合成破綻の主原因のため。
- すべての素材にライセンスと出典URLを保存する。CC0やパブリックドメインを優先し、サイトごとの規約(再配布やAI利用の制限)は取り込み前に確認する。

事前処理(素材1枚につき1回):

1. 取得と正規化: 長辺を上限に合わせて縮小し、元解像度は保持する。
2. 埋め込み: CLIP系の画像埋め込みを計算し、ベクトル索引(FAISSなど)に登録する。
3. 切り抜き: SAMで主役マスクを作り、アルファ付きPNGとして保存する。面積比・中心からの距離・マスク数(ごちゃつき)・縁の滑らかさを計算する。
4. 属性判定: Clefで属性を判定して保存する(「パッチ選択」「Clef/Clairicの使い方」参照)。
5. 登録: 素材レコードをDB(SQLite案)に保存する。

素材レコード(案):

| 項目 | 内容 |
| --- | --- |
| id / pool | 素材ID、所属プール(スタイル) |
| source_url / license | 出典とライセンス表記 |
| embedding_id | ベクトル索引上の位置 |
| cutout_path / bbox | 切り抜きPNGと外接矩形 |
| area_ratio / centrality / clutter / edge_score | SAM由来の機械的な指標 |
| attrs | Clefの属性判定(主役・見切れ・向き・光の方向・スタイル・透かし/文字・縁のきれいさ)と確率 |
| judge_version | 判定に使ったモデルと質問セットの版(再計算の判断用) |

## ClefとClairicの使い方

Clefは選択と採点を担当する判定モデル、Clairicは数値を出す抽出モデルとして分担する。どちらも文章を生成せず、確率や型付きの値だけを返す。

確認済みの仕様:

- Clef: 質問の型は3種類。`noul`(はいの確率)、`choice`(選択肢ごとの確率と確信度)、`score`(順序付きの評価基準での確率重み付きスコアと各段階の確率)。1リクエストで最大 64 問。状態と一緒に最大4枚の画像を渡せる。
- Clairic: テキストと最大4枚の画像から、名前と型を指定した項目(数値・日付・リスト・推定値)を埋め、各項目に確信度か80%範囲が付く。2026-10-19公開のプレビュー。
- 呼び出し: Workers AIの REST API(`/ai/run/@cf/cloudflare/clef` 等)。トークンはWorkers AIのReadとEditが必要。PythonからはRESTで呼ぶ。質問の正確なリクエスト形式は実装前に公式ドキュメントで確認する。

用途と質問設計(案):

| 用途 | モデル | 型 | 質問の例 | いつ |
| --- | --- | --- | --- | --- |
| 主役の確認 | Clef | noul | 主役は「犬」か | 事前 |
| 見切れ | Clef | noul | 主役が画面端で切れているか | 事前 |
| 透かし・文字 | Clef | noul | 透かしや文字が入っているか | 事前 |
| 向き | Clef | choice | 正面 / 左 / 右 / 後ろ / 不明 | 事前 |
| 光の方向 | Clef | choice | 左 / 右 / 上 / 正面 / 不明(素材と背景の両方) | 事前・実行時 |
| スタイル | Clef | choice | 洋画 / 日本画 / イラスト / 写真 | 事前 |
| 切り抜きの縁 | Clef | score | 縁のきれいさ 1–5 | 事前 |
| 位置・大きさ・回転 | Clairic | 数値項目 | x, y, z(手前–奥), scale, rotation + 80%範囲 | 実行時 |
| 合成結果の自然さ | Clef | score | 光・大きさ・向きの自然さ 1–5 | 実行時 |

呼び出し予算の方針(案):

- 無料枠は全モデル共通の1日10,000ニューロン(00:00 UTCリセット)。ClefとClairicの1回あたりの消費と、プレビューのモデルが枠の対象かは未確認。M0で実測する。
- 結果は(画像ハッシュ, 質問セットとモデルの版)をキーにキャッシュする。事前判定は最初の1回だけ。
- 1リクエストに質問をまとめる(最大 64 問)。実行時の遅延重視の箇所はClef-flashを検討するが、画像入力に対応するかは未確認。
- 枠を超えたときは、CLIPのスコアと機械的指標だけで動く縮退モードに落とす。

実装の境界(案): `Judge`(選択・採点)と `Estimator`(数値推定)の2つのインターフェースを切り、最初はCloudflareのREST実装で埋める。Clefの重みはApache 2.0でHugging Faceにあるため、将来ローカル実装に差し替えられる。

## パッチ選択

Sketch2Photoの「フィルタで候補を絞り、組み合わせに点を付けて最良を選ぶ」挙動を、事前計算した指標と属性で再現する。以下の数値はすべて初期値の案で、M2で素材を見て調整する。

1. 要素分解: 文章を要素のリスト(名前、役割=背景/主役/小物、検索語、プール)に分ける。Clairicのリスト項目でできるかを検証し、難しければ規則か別のモデルにする。
2. 検索: 要素ごとに、指定プールの索引からCLIP類似度の上位K件(K=50)を取る。
3. 機械的な足切り: DBの指標で落とす。主役マスクの面積比が極端に小さい/大きいもの、中心から遠いもの、マスク数が多い(ごちゃつき)もの、解像度が配置サイズに対して不足するもの、縁スコアが低いもの。
4. 属性フィルタ: Clefの属性でさらに落とす。主役確率が低い、見切れ確率が高い、透かし・文字の確率が高いもの。
5. 単体スコア: unary = CLIP類似度、縁スコア、主役確率の重み和。要素ごとに上位M件(M=5)を残す。
6. 組み合わせ選択: 要素数は6程度を上限とし、候補の組をビーム探索(幅B=10)で選ぶ。合計点 = 単体スコアの和 + 素材同士の相性の和。相性は光の方向の一致(choiceの確率ベクトル同士の積)、色味の距離(Lab平均またはヒストグラム)、スタイルの一致、スケールの整合。背景画像がある場合は背景の光との一致を優先する。
7. 左右反転の救済: 光の方向が逆で、反転しても不自然でない物体(Clefのnoulで「左右反転して不自然か」を事前判定)は、反転して再評価する。
8. 出力: 上位N組(N=3)を合成に渡す。選ばれなかった候補は、再試行用に保持する。

Sketch2Photoのフィルタの詳細(顕著性・ごちゃつきの具体的な基準)は第三者の解説でしか確認していない。実装前に論文のPDFで基準を確認し、上の3と入れ替える。

## 配置・切り抜き・合成

選ばれた素材の組を、位置推定→変形→重ね順→なじませの順でキャンバスに載せる。ここから先は画素を扱うため、Clef/Clairicは判断と数値のみを担当し、実際の変形と合成は通常の画像処理で行う。

1. 位置推定: Clairicに要素ごとの x, y, z(手前–奥の順位), scale, rotation を数値項目として尋ねる。入力は文章と背景画像(あれば)。各値に付く確信度か80%範囲を保存する。
2. 粗→精の絞り込み: 80%範囲が広い項目は、候補領域を切り出してもう一度尋ねる(最大2回を案とする)。それでも広いときは、格子分割の候補をClefの採点で選ぶ。
3. 変形: scaleとrotationを素材の切り抜きPNGにアフィン変換で適用し、必要なら左右反転する。
4. 重ね順: zの順位で奥から手前へ重ねる。奥行きのある場面では、単眼の深度推定モデルで背景の深度を出して補助とする。
5. なじませ: スタイルプールごとに方式を切り替える。絵画・イラスト系は縁の羽根ぼかしとアルファ合成を基本にする(継ぎ目が見えても作風として成立しやすい)。写実プールはポアソン合成(OpenCVのseamlessClone)と影の追加を基本にする。
6. 挿入モデル(任意、後続フェーズ): 写実プールで継ぎ目や影が気になるときに、Paint by Exampleのような参照画像付きインペインティングを使う。ライセンスと顔の非対応が制約になる(「ベース実装」参照)。

座標の規約(案): x, y はキャンバス幅・高さを 0–1 に正規化した値、z は整数の順位、rotation は度(時計回り)とする。Clairicへの問い合わせでもこの規約を明示する。

Clairicが画像から「置くのに自然な位置」をどこまで正確に推定できるかは未検証。M3の最初の実験で確かめ、低い場合の代替案として、格子候補をClefの採点で選ぶ方式を用意する。

## 評価と再試行ループ

Sketch2Photoが合成結果に数値の点を付けて最適な組み合わせを探した考え方を、複数の評価軸の重み和で再現する。

評価軸(案):

| 軸 | 計算 | 役割 |
| --- | --- | --- |
| 意味の一致 | 合成画像と要望文のCLIP類似度 | 要望から外れていないか |
| 自然さ | Clefのscore(光・大きさ・向きの自然さ 1–5) | 継ぎ目や違和感の検出 |
| 一貫性 | 素材間の色味・スタイル・光の距離 | トーンのばらつき |
| 縁の品質 | 合成後の境界帯のエッジ指標 | 切り抜きの粗さ |

ループ(案):

1. パッチ選択の上位3組をそれぞれ合成して点数を出す。
2. 合計点が閾値以上のものがあれば、最高点を採用して終了。
3. なければ、自然さスコアが低い原因の要素(点数の分解で特定)を候補の次点と入れ替えて再合成する。
4. 再試行は最大3回。超えたときは、最高点の候補を「要確認」として返す。

ログ: すべての試行について、採用素材、変形パラメータ、各軸の点数、呼び出し回数をJSONで保存する。重みや閾値の調整はこのログと目視を突き合わせて行う。

重みや閾値は初期値を決めていない。M4で、人が「良い」と判断する結果と点数がよく相関するように調整する。

## ベース実装とライセンス

2つの既存実装はどちらも開発が止まっているため、パイプラインの中核にはしない。後続フェーズで、仕上げ役として任意に追加する。

| 部品 | 役割 | 確認できた事実 | 扱い |
| --- | --- | --- | --- |
| CLIP-CLOP (google-deepmind/arnheim の Arnheim 3) | パッチ配置の勾配最適化 | Apache 2.0。約2,800行。`arnheim_3/src` に collage.py / collage_generator.py / patches.py / rendering.py / training.py / transformations.py。CLIPは設定で切り替え(既定 ViT-B/32)。`--no-cuda` でCPU実行も可。サンプルパッチはCC BY 4.0(Fruit and veg のみ CC BY-SA 4.0) | M5で、こちらの配置結果を初期値にして細部を詰める用途で試す。ライセンス表示を保持して取り込む |
| Paint by Example | 参照画像付きの挿入となじませ | Stable Diffusion v1.4 を初期値にした公開チェックポイント(Fantasy-Studio/Paint-by-Example)。diffusers の PaintByExamplePipeline が image / mask_image / example_image を受ける。GitHubの最終更新は約2年前。ライセンス表示は「other」。ModelScope版は屋外の自然風景向けで顔未対応、推論はGPUのみと記載 | 製品に使う前にLICENSEを読む。参照画像は元のREADMEではMSCOCOから手動で探しているので、ここをこちらの自動検索で置き換える |
| CLIP / SAM | 埋め込みと切り抜き | ライセンスはこの資料を作る過程では確認していない | 採用前に各リポジトリのLICENSEを確認する |

CLIP-CLOPの初期化は元々ランダムで(各パッチの色変換とアフィン行列をランダムに初期化)、こちらの配置を初期値として注入できるかは未確認。`collage_generator.py` と `training.py` を読んで判断する。できない場合は、初期化部分を改造するか、自前の簡易最適化で代用する。

Paint by Exampleの土台がStable Diffusion v1.4と古い点は品質面の限界になる可能性がある。新しい同種のモデルがあるかは未調査で、M5の前に調べる。

## 検証計画とマイルストーン

各段階に「次へ進む条件(ゲート)」を置く。ゲートの数値はすべて初期の案で、結果を見て見直す。

1. M0 環境と基準: リポジトリ構成(案: `pipeline/` `adapters/` `data/` `scripts/`)、設定ファイル、Judge/Estimatorのインターフェースを作る。Colabで Arnheim 3 をサンプルパッチで動かし、基準の出力と速度を記録する。ClefとClairicの1回あたりの消費ニューロンを実測する。ゲート: ClefとClairicをRESTで呼び、画像1枚に対する結果をログに残せる。
2. M1 素材プール: 1プール(例: 美術館のオープンアクセス絵画)約200枚を取り込み、埋め込み、SAM切り抜き、Clef属性判定、DB登録を行う。ゲート: 目視で切り抜きの良し悪しを確認し、属性判定と自分の判断がどの程度一致するかを数値化する(一致率の目安 80%以上を案)。
3. M2 パッチ選択: 要素分解、検索、足切り、組み合わせ選択を実装し、要望文ごとに上位候補を一覧(コンタクトシート)で確認できるようにする。ゲート: 10件の要望で、上位3組のうち少なくとも1組が自分から見て「使える」。
4. M3 配置と合成: 最初に位置推定の検証実験を行う。位置が既知の合成画像(物体を決めた座標に貼ったもの)を数十枚作り、Clairicの推定値と真の座標の相関(Spearman)と誤差を見る。相関が低ければ、格子候補をClefで選ぶ方式に切り替える。その後、変形・重ね順・なじませを実装する。ゲート: 相関の目安 0.7以上を案とするか、代替方式で同等の精度が出ること。
5. M4 評価ループ: スコアと再試行を実装し、ログと目視を突き合わせて重みを調整する。ゲート: 再試行なしの結果より、ありの結果の方が自分から見て改善していること。
6. M5 拡張: スタイル別プールを増やす、素材がない要素の生成フォールバック、CLIP-CLOPによる細部の最適化、Paint by Exampleによる縁の仕上げ、部品差し替えUI。ゲート: フェーズごとに個別に決める。

## 未確認事項とリスク

## 設計レビューの論点(未反映・未決)

2026-10-31 に別モデルで批判的にレビューした結果。**本文にはまだ反映していない。** どれを採用するかは決めていない。レビューは設計書と骨組みの読解に基づき、外部仕様は確認していない。

主な問題:

1. **配置の検証が本番の課題とずれている。** M3の実験は「貼った座標を当てる」で、本番の「まだ置いていない物体の置き場所を提案する」とは別の課題。配置の入力に選んだ素材の形が入っていない。パッチ選択が配置サイズより前に「配置サイズ」で足切りしており、順序が矛盾している。不確実性が最大なのに検証が M1・M2 の後。
2. **素材の網羅性が薄い。** 約200枚のプールで K=50 なら検索が絞り込みにならない。埋め込みは元画像全体、貼るのは主役マスク1つで、検索の対象と貼る対象がずれる。「主役は『犬』か」は、取り込み時に要望文が分からないので事前判定にできない。
3. **成功基準と評価指標が未確定。** 「意味の一致」が検索と同じCLIP類似度の繰り返し。Clefの自然さ判定の精度が未確認事項の表にない。再試行の「原因要素の特定」の方法が未定で、差し替えるのは素材だけ(配置は見直さない)。ゲートが主観のみ。

その他の指摘:

- ビーム探索は不要(M=5、要素6つで 5^6 = 15,625 通り)。それより上位3組が似た組になる問題への対策が要る。
- 欠けている部品: 色合わせの補正、背景の作り方、キャンバス定義、座標規約(中心か接地点か)、深度推定モデルの計画、顔除外の仕組み。
- 縮退モードでは配置ができない。1回の実行での呼び出し回数の見積もりがない。
- 規則ベース配置(役割別テンプレート)を基準かつ縮退モードにする案。
- 重み和の前に正規化が要る。閾値での終了は較正なしでは機能しない。
- M1の一致率80%は偏りのある属性では甘い(適合率・再現率で測る)。M3のSpearmanは位置の指標として不適切。
- 骨組みの `Judge` は1問ずつしか聞けず、64問まとめ送信ができない。結果にモデルの版・消費量が付かない。予算超過の例外がない。工程単位(`Placer` / `Tagger` / `Critic`)に切る案。
- (後回し中の権利)NDの素材は除外が必要、BY / BY-SA の出力物側の義務、外部AIへの送信可否。

マイルストーン並べ替えの案(未決):

1. M0: API調査(形式・消費量・上限)と、成功基準・ベンチマーク用要望文(20件程度)の固定。Arnheim の実行は M5 へ。
2. M0.5: Clef/Clairic を使わない最小の通し実装(手で選んだ切り抜き、切り抜き単位のCLIP検索、規則ベース配置、アルファ合成)。基準かつ縮退モード。
3. 配置方式の比較実験を、本番に近い課題で行う(実写から物体を除いて元の位置を当てさせる、など)。
4. 素材の網羅性の確認(要望の各要素について、使える切り抜きが上位K件に入る率)。
5. 属性判定、パッチ選択、評価指標の検証と評価ループ、拡張。
