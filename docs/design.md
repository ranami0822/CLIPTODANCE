# 画像検索コラージュAI 設計方針(実装用)

Oct 31, 2026 · @Ryuuichiro

## 目標と前提(2026-10-31 決定)

- **目標**: 切り貼りが見えてよいコラージュ。ただし抽象画ではなく、全体として「ある程度、風景として成立している」もの。継ぎ目を完全に消す写実的な合成は目標にしない。
- **利用**: 個人利用。
- **権利**: 一旦後回し。ただし素材ごとの `source_url` / `license` の記録は残す(後から整理できるようにするため)。公開・共有、素材を外部サービスへ送る範囲の見直しなどの前に再検討する。

この前提から出てくる影響(以下は私の推測で、未決):

- 「自然さ」の意味は、「写真として本物に見える」ではなく「風景として破綻しない」(地平線・地面との接地・遠近とスケールの整合・重なり順)に寄せる。評価軸の「自然さ」(後述)の質問文もこれに合わせて直す必要がある。
- なじませは羽根ぼかし+アルファ合成を基本にし、ポアソン合成やPaint by Exampleは優先度を下げる(後続フェーズ)。
- 「地平線の位置」「地面の領域」を配置の入力に持つ必要があるかもしれない。背景に全面で使う素材の扱いも決める必要がある(未決)。

## 風景ルール(配置の骨格)

「風景として成立する」ための最小ルール。**R1〜R3 は決定、R4〜R9 は私の案(未決)。** 数値はすべて仮置き。

### 決定

- **R1 土台**: 風景画像1枚を土台(背景)にし、その上に切り抜きを置く。背景画像の指定があればそれを使う。なければ背景用の風景素材を1枚選ぶ。
- **R2 キャンバス**: 横長 3:2。土台をこの比率で切り出して使う。
- **R2a 切り出しでの地平線の位置**: 土台を切り出すとき、地平線を**下の三分の一**(画面の高さの約 2/3、`y_h' ≈ 0.667`)に置く。空が画面の上 2/3 を占める。
  - 窓の高さを元画像の高さの `c` 倍にすると、`y_h'` を 2/3 にできる条件は `c ≤ min(1, 1.5·y0, 3·(1−y0))`(`y0` = 元画像での地平線の位置、上が 0)。元画像の地平線が高い(`y0` が小さい)と、拡大して切り出すことになり、解像度が下がる。
  - 切り出し窓は、`c` が下限(仮置き 0.6)以上の範囲で、`y_h'` を 2/3 に最も近づける。届かない土台は、ずれが許容(仮置き ±0.08)を超えたら減点か除外する。Sketch2Photo も、地平線がキャンバスと30%以上ずれた背景を捨てている。
- **R3 遠近**: 地平線の高さ `y_h` を1つ決め、物体の足元(接地点)の位置からサイズを決める。足元が画面の下にあるほど大きく、地平線に近いほど小さい。空を飛ぶ物(鳥・雲・月など)は例外として、空の領域に置く。

- **R3a 地平線 `y_h` の決め方**:
  - プールの風景素材: 取り込み時に自動で推定して素材レコードに保存し、一覧(コンタクトシート)で目視確認して、外れたものだけ手で直す。
  - 持ち込み背景: 実行時に推定し、推定値の線を画像に重ねた確認画面で、ずれていれば直してから進む。
  - ここでの `y_h` は、視線の高さの地平線(消失線)。山・森・建物越しに見える空との境界(スカイライン)とは一致しない。丘や山があると、スカイラインは `y_h` より上に出る。
  - 推定の方法(決定): OpenCV などの軽い処理で、空と地面の境界(スカイライン)から初期値を出す。Clairic・Clef・深度推定は使わない。山・森・建物などでは消失線とずれる見込みなので、そこは目視で直す前提。
  - 具体的な処理(色・勾配の見方など)は未定。M1 で手で付けた正解と比べて、直す手間を見る。
  - 参考(Sketch2Photo の論文本文で確認): 背景を風景画像に限り、候補の背景ごとに地面平面の推定([Saxena et al. 2008] の方法)で地平線を求め、キャンバスの地平線と画像の高さの30%以上ずれたものを捨てる。キャンバス側の地平線の既定は中央の高さで、ユーザーが調整できる。こちらは、土台を選んでから `y_h` に合わせて物のサイズを決めるので、順序が逆。土台選びの条件に `y_h` を使うかは未決。

- **R10 役割分担(Clairic が提案し、規則が補正する)**:
  - Clairic が出す項目: 要素ごとの `x`、足元の `y`、スケールの倍率、`rotation`、(物の実寸の高さ `H_m` は種類別の表から引き、表にない種類のときだけ Clairic が提案する)。それぞれに確信度か80%範囲が付く。
  - 規則が行うこと: `z` は足元の `y` から決める(R6)。スケールの基準は R5 で決め、Clairic の倍率は範囲内(仮置き 0.5〜2.0)に収める。`rotation` も範囲内(仮置き ±15°)に収める。領域(R4)・はみ出しと重なり(R8)に合わない提案は補正する。補正した事実と量はログに残す。
  - 規則だけで動く縮退モードは設けない(2026-10-31 決定)。Clairic の提案が得られないときはエラーとして扱う(再試行の方法は未決)。
  - 検証: Clairic の提案の当たり具合を、規則による補正量と目視での良し悪しで見る。M3 の最初の実験(座標を当てる実験)は、この検証に置き換える方向。検証計画の M3 本文は未改訂。

### 案(未決)

- **R4 領域**: 画面を `y < y_h` の空と `y >= y_h` の地面に分ける。地上の物は足元を地面領域内に置く。水面や建物の屋上などの扱いは、まず対象外にする。
- **R5 サイズ**: 地上物の画面上の高さを `h = (H_m / Hc) * (y_foot - y_h)` とする(H_m = 物の実寸の高さ、Hc = カメラの高さ、y は画面高さに対する 0–1)。Hc の仮置きは 1.6m。実寸 `H_m` は種類別の表(平均と幅。`configs/height_table.yaml`)から引き、表にない種類だけ Clairic に尋ねる(2026-10-31 決定。Photo Clip Art が種類別の高さ分布を使うのに倣う)。
- **R6 重ね順**: 地上物は `y_foot` が小さい(奥の)ものから先に重ねる。山・雲・月・太陽は最奥にする。
- **R7 構図**: 主役は三分割の交点の近くに置くことを目安にする。地上の主役の高さは画面の 25〜60% 程度を目安にする。**どちらも目安で、規則の検査(補正・除外)には使わない**(2026-10-31 決定)。評価の弱い項として扱い、重みは M4 で人の判断と合わせて調整する。
  - **R2a との衝突(目安にとどめる方針で解決。2026-10-31 決定)**: 地平線が 2/3 にあると、地面は画面の下の三分の一しかない。R5 で計算すると(カメラ高さ 1.6m)、人(1.7m)は足元が最下端でも画面高さの約 35%、25% に届くには足元が `y ≥ 0.90` 付近でなければならない。犬(0.5m)は最大でも約 10%。木(8m)や家(6m)は足元が `y ≈ 0.85` で画面高さの約 70〜90% になり、はみ出しやすい。主役が人や動物のときに 25% を求めるのは無理がある。対応: 範囲は目安にとどめ、規則の検査には使わない。主役が人や動物のときに高さが目安を下回っても、補正も除外もしない。カメラ高さ(R5)は 1.6m のまま。
- **R8 重なりとはみ出し**: 物同士の重なりは面積の 30% まで。キャンバス外へのはみ出しは原則不可。
- **R9 なじませ**: アルファ合成+羽根ぼかしを基本にし、色補正を加える。色補正は Reinhard 2001 の方式(lαβ 色空間で各軸の平均と標準偏差を合わせる)を、切り抜きと配置位置の周辺の領域の間で行い、強さ(0〜1。0.2 を仮置き)で弱める(2026-10-31 決定)。光の向きは土台と合わせ、逆なら左右反転で救済する。

### 座標の規約(案、上記に合わせて更新)

- 地上物: `(x, y)` = 足元中央(接地点)。空中物: `(x, y)` = 中心。
- `x, y` はキャンバス幅・高さに対する 0–1。上が y=0。
- `scale` は R5 で決まる高さを基準とした倍率(1.0 = 規則どおり)。`rotation` は度(時計回り)で、足元(空中物は中心)を回転の中心とする。

## 既存研究で確認したこと(風景ルールの根拠)

2026-10-31 に調査。「本文」は論文のPDFを取り出して読んだもの、「抜粋」は検索結果の要約のみ(論文本体は未読)。

| ルール | 既存研究 | 確認の度合い |
| --- | --- | --- |
| R3 / R5 地平線と足元からサイズを決める | Photo Clip Art(Lalonde 2007): 地面に立つ物の3D高さ `y_i = y_c · h_i / (v0 − v_i)`(`y_c` = カメラ高さ、`v0` = 地平線位置、`v_i` = 足元の位置、`h_i` = 画像上の高さ。`v` は画像の下端から測る)。前提は「物が地面に立つ」「地面が横に傾かず、画像面にほぼ直交」。Hoiem 2006/2008 の式を使用 | 本文(Photo Clip Art)。Hoiem は取得したが関連箇所のみ |
| R5 カメラ高さの既定 1.6m | Photo Clip Art の事前値: 地平線は画像の中央、カメラ高さの平均は 1.6m(目の高さ程度) | 本文 |
| R5 物の実寸 | Photo Clip Art は、種類ごとの高さの分布を**データから推定**して使う(同種の物が15個以上あれば正規分布を推定)。物ごとにモデルへ尋ねる方式ではない | 本文 |
| R3a 地平線の与え方 | Photo Clip Art: 新しい写真ではユーザーが線を引いて指定する。ほかのカメラ値は最尤値かEXIF。Sketch2Photo: 既定は中央の高さ、ユーザーが調整可。どちらも**人の指定が基本** | 本文 |
| R3a 自動推定 | 従来の幾何的方法は消失点などの手がかりが要る。Workman 2016 は CNN で地平線を直接推定し、新データセット HLW(100,553枚)で従来法を上回ると主張。ただし HLW は観光地の建物中心で、森・畑・住宅地の画像はほとんどない | 本文(HLW)。性能の数値は読んでいない |
| 素材の光の合わせ方 | Photo Clip Art: 画像を空・垂直面・地面に分け、それぞれの Lab 色のヒストグラムの χ² 距離を重み付きで足す。空が最も重要、次に地面、垂直面はほとんど効かない | 本文 |
| 切り抜きの品質 | Photo Clip Art: 切り抜きの境界の頂点数(ラベル付けのクリック数)で並べるだけの単純な方法。合成は graph-cut + Poisson に、局所文脈の項と影の検出を追加 | 本文 |
| 配置位置の自動提案(R10) | 学習ベースの物体配置: FOPA(位置ごとの妥当性を一度の推論で出す)、TopNet(位置と大きさの3次元ヒートマップを出し、スライディングウィンドウより10倍以上速い。学習は注釈付きデータか、インペイントで作った合成データ)。TopNet 自身が、3D・照明・影を扱わないこと、インペイント画像と自然画像の差があることを限界に挙げている。LLM に位置と大きさを CSS 形式で出させる LayoutGPT は、CLIP で選んだ類似例を例示に使う | 本文(概要・方式・限界を読んだ。データセット規模・公開状況は未確認) |
| CLIP 類似度で位置関係を評価できるか | 視覚言語モデルは語順・関係・属性の結びつけに弱い(ARO ベンチマーク。冒頭で CLIP が「馬が草を食べる」と「草が馬を食べる」を区別できるかを問い、CLIP の ViT-B/32 を難例で再学習した NegCLIP と比べている) | 本文(概要・実験設定) |

追加調査(2026-10-31、論文本文を読んだもの):

| 対象 | 確認したこと |
| --- | --- |
| Reinhard 2001(色の転送) | lαβ 色空間は軸どうしの相関が小さい。各軸の平均と標準偏差を合わせるだけの単純な方法 |
| Deep Painterly Harmonization(Luan 2018) | 写真の物を絵画に貼る問題。普通の合成では「コラージュに見える」と指摘。局所の統計を転送する。500×500 の画像で約5分(K80 GPU)。実装は「採択後に非商用の研究用に公開予定」と記載(公開されたかは未確認) |
| AutoCollage(Rother 2006) | 複数の写真から1枚のコラージュを作る。画素ごとのラベル付けをエネルギー最小化で解く(重要度・顔を保つ・空は重視しない等の項)。つなぎ目は graph-cut と Poisson 合成で隠す。統合最適化でなく、段階的な最適化の列にしている |
| LayoutGPT(2023) | GPT-3.5/4 にテキストから CSS 形式で位置と大きさを出させる。CLIP で選んだ類似の例を例示に使う。例示に使うレイアウトのデータが要る |
| 構図(三分割など) | 景観写真で、三分割・黄金分割・地平線の位置が見た目の評価を変える、という研究の概要を1件確認(論文本体は未読)。写真指南は「地平線を中央に置かない」を勧める。Liu 2010 は顕著領域を三分割の交点に寄せる最適化(概要のみ) |

### 採否の決定(2026-10-31。反映済みか、保留かを分けて記す)

採用:

1. **物の実寸は種類別の表**にする(平均と幅)。表にない種類だけ Clairic に尋ねる。表の値は手で作るので、出典を値ごとに記録する。→ R5・R10 に反映、`configs/height_table.yaml` を追加。
2. **光の相性に、元画像と土台の Lab ヒストグラムの χ² 距離を加える。** Clef の光の方向の選択は併用する(精度は未検証)。Photo Clip Art では、空が最も効き、次に地面で、垂直面はほとんど効かなかった。こちらは当面、画像全体で比べ、空・地面の分割は後で検討する。→ パッチ選択6に反映。
3. **色補正は Reinhard 方式**(lαβ の平均・標準偏差の転送。強さで弱める)。→ R9 に反映。
4. **評価の「意味の一致」は、物の有無と作風に限る。** 位置関係は CLIP で測れない前提にして、規則の検査と目視で見る。→ 評価軸に反映。

保留(M5以降の比較候補):

5. **学習済みの配置モデル(TopNet、FOPA)**: 論文本文から、学習済みの重みの有無とライセンスを確認できなかった。TopNet 自身が3D・照明・影を扱わず、学習データが写真(インペイント合成を含む)である限界を挙げている。こちらは絵画・風景で、遠近を規則で守る方針なので、当面は使わない。
6. **LayoutGPT 型の LLM レイアウト**: 風景コラージュのレイアウト例がこちらにないので、例示づくりが先に要る。R10 の Clairic 提案との比較候補として残す。
7. **Deep Painterly Harmonization**: 絵画プールの仕上げ候補。重い(約5分)うえ、実装の公開状況とライセンスが未確認。
8. **AutoCollage**: 参考のみ。問題の設定(複数の写真を並べる)が、物体の切り抜きを風景に置くこの設計と異なる。段階的な最適化の列にする作りは、こちらの段階的パイプラインと同じ方針。

案のまま維持:

9. **R7 構図(三分割・主役の高さ)**: 根拠が弱い(概要1件と写真指南)。硬い制約にせず、目安として評価の弱い項に使う(決定)。重みは M4 で人の判断と合わせて調整する。土台を 3:2 に切り出すときの地平線は、下の三分の一に置くと決定(R2a)。

## 目的とスコープ

テキストの要望(任意で背景画像とスタイル名)から、検索した既存画像の切り抜きを配置・合成して1枚のコラージュを作るパイプラインを、Python(PyTorch)で実装する。生成モデルは学習せず、検索・判断・合成の部品を組み合わせる。

- 入力: 要望の文章。任意で、背景画像、素材プール名(洋画・日本画・イラストなど)、要素数の上限。
- 出力: 合成画像(PNG)と、採用した素材ID・変形パラメータ・各スコアを記録したJSONログ。
- 作らないもの: モデルの学習、実行時のWebスクレイピング、顔を含む写実合成(Paint by Exampleが顔を未対応とされるため)。
- 実行環境: GPUのある自分のPCかColabを本番とする。Claude側のクラウド環境はGPUなし(CPU 2コア、メモリ7GB)で、小規模な前処理と動作確認までを想定する。

## 基本方針

既存論文や実装の「挙動」(何をどの順でやるか)だけを倣い、中身の部品は現代のものに置き換える。

借りる挙動:

- Sketch2Photo(2009): スケッチと文字ラベルから、ネットで見つけた写真を縫い合わせる。不適切な検索結果をフィルタで除き、合成結果に数値の点を付けて最適な組み合わせを選び、最後に人が対話的に直す。
- Photo Clip Art(2007): 物体を加工して合わせるのではなく、向き・光・解像度が合う物体をライブラリから検索して選ぶ。
- CLIP-CLOP(2022): 人が素材(パッチ)のライブラリを用意し、評価役(CLIP)が構図を採点して最適化する。人が場を手で直せる余地を残す。

置き換え:

| 論文・既存実装の要素 | 現代版の部品 |
| --- | --- |
| 手描きスケッチとラベル(配置の指定) | Clairicが文章から物体ごとの位置・大きさ・回転と確信度を出す |
| ネット画像検索 | 事前に索引化した素材プールをCLIP系埋め込みで検索 |
| 不適切画像の除外フィルタ | SAMのマスク特徴量で足切り + Clefの属性判定(はい/いいえ・選択・採点) |
| 顧著性とGrabCutによる切り出し | SAM |
| 継ぎ目のない合成 | 縁のぼかしとポアソン合成(OpenCV)。写実プールではPaint by Exampleを任意で追加 |
| 合成結果の点数と最適な組み合わせの探索 | CLIPの一致度 + Clefの自然さスコア + 素材間の相性。上位候補での探索 |
| 対話的な修正 | 後続フェーズ。「この部品だけ差し替え」のUI |

設計の原則(案): 判断(Clef/Clairic)と画素処理(SAM/OpenCV)を分離し、判断側はadapter経由にして、ローカルCLIPや他のモデルに差し替えられるようにする。

## パイプライン全体

## 素材プールと事前処理

素材は実行時に集めず、事前に集めて索引化する(権利管理と呼び出し費用を抑えるため)。

プールの方針:

- スタイル別(洋画・日本画・イラスト・写真など)に分け、コラージュ1作品の中では原則同じプールから選ぶ。光や質感のばらつきが合成破綻の主原因のため。
- すべての素材にライセンスと出典URLを保存する。CC0やパブリックドメインを優先し、サイトごとの規約(再配布やAI利用の制限)は取り込み前に確認する。

素材の単位(2026-10-31 決定。既存研究に倣う):

- 検索する単位と貼る単位を、どちらも**切り抜き**にそろえる。1枚の画像から複数の切り抜きを作り、切り抜きごとに埋め込みを計算して検索する。
- 根拠(確認した事実):
  - CLIP-CLOP(Arnheim 3)は、パッチ(切り抜き)を事前に用意し、検索はせず全パッチを最適化に渡す。`arnheim_3_patch_maker.ipynb` は、PixelLib の Mask R-CNN(COCO)で画像ごとに検出した物体を別々のパッチとして切り出して保存する(READMEにも "pretty basic" と書かれている)。1枚から複数のパッチを作る点がこの決定の元になった。
  - Sketch2Photo は検索の結果から、背景が単純で「アルゴリズムに優しい」画像だけを残し、その中の顕著な物体を切り出す(後述の足切り基準)。検索で当たった物と貼る物がずれる画像は、そもそも捨てる設計になっている。
- 土台(風景)用には、画像全体の埋め込みを別に持つ。
- これにより、事前判定の「主役は『犬』か」(取り込み時には要望が分からないので成り立たない)は、検索後の上位候補に対する実行時の確認に変える。

事前処理(素材1枚につき1回):

1. 取得と正規化: 長辺を上限に合わせて縮小し、元解像度は保持する。
2. 切り抜き: SAMで物体ごとのマスクを複数作り(1枚から複数)、アルファ付きPNGとして保存する。面積比・中心からの距離・マスクの周囲のごちゃつき・縁の滑らかさを、切り抜きごとに計算する。
3. 埋め込み: 切り抜き(マスクで切り出した画像)ごとにCLIP系の埋め込みを計算し、ベクトル索引(FAISSなど)に登録する。土台用には画像全体の埋め込みも別に計算する。
4. 属性判定: Clefで属性を判定して保存する(「パッチ選択」「Clef/Clairicの使い方」参照)。
5. 登録: 素材レコードをDB(SQLite案)に保存する。

素材レコード(案):

| 項目 | 内容 |
| --- | --- |
| id / pool | 素材ID、所属プール(スタイル) |
| parent_image_id / role | 元画像のID、役割(土台=風景 / 切り抜き) |
| source_url / license | 出典とライセンス表記 |
| embedding_id | ベクトル索引上の位置 |
| cutout_path / bbox | 切り抜きPNGと外接矩形 |
| area_ratio / centrality / clutter / edge_score | SAM由来の機械的な指標 |
| attrs | Clefの属性判定(主役・見切れ・向き・光の方向・スタイル・透かし/文字・縁のきれいさ)と確率 |
| horizon_y / horizon_checked | 土台として使う風景素材の地平線の高さ(0–1、上が0)と、目視確認済みか(R3a) |
| judge_version | 判定に使ったモデルと質問セットの版(再計算の判断用) |

### 実装(M1。`pipeline/pool/`、`scripts/pool.py`)

- **取得元**: The Met Open Access(CC0)。検索は `v1.1/search`(offset / limit。旧 `v1/search` は 2026-10-01 に廃止)。`isPublicDomain` で画像のあるものだけを使い、元画像(`primaryImage`)を `originals/` に保存する。Art Institute of Chicago の API は、この環境からは 403 で届かなかった(Rijksmuseum の旧 API は 410)。
- **流れ**: 元画像 → **額縁・余白の除去** → 作業用画像(長辺 2048 以下)→ 地平線の初期値(OpenCV)→ SAM で候補マスク → 指標を計算 → 足切りと重複除去 → 切り抜き PNG(RGBA)→ CLIP 埋め込み(画像全体と切り抜きごと)→ DB。
- **DB**(`data/pool/<pool>/pool.sqlite`): `images`(出典・ライセンス・地平線・全体の埋め込み)と `cutouts`(元画像への参照・外接矩形・指標・埋め込み・属性・判定の版)。索引は DB の埋め込みから FAISS で作る。
- **指標の定義**(すべて初期案): `area_ratio` = マスク面積 / 画像面積。`centrality` = 重心と画像中心の距離 / 半対角線。`clutter` = マスク周囲の帯(長辺の 3%)と交わる Felzenszwalb セグメントの数(Sketch2Photo の基準を、帯の幅を画像サイズに対する比にして再現)。`edge_score` = 平滑化した輪郭の長さ / 生の輪郭の長さ(1 に近いほど滑らか)。`border_touch` = 外接矩形が画像の端に接する辺の数。`aspect` = 最小外接回転矩形の長辺 / 短辺。`thickness` = その短辺 / 画像の長辺。`backdrop_frac` = マスクのうち余白にかかる割合(保存はせず足切りに使う)。
- **足切り**(初期案): 面積比 0.004〜0.6、`aspect` ≤ 8、`thickness` ≥ 0.02(額縁の帯・柱・水平線のような細長い帯を落とす)、`backdrop_frac` ≤ 0.2、重複(IoU 0.85 以上)の除去、1 枚あたり最大 12 個。
- **額縁・余白の除去**(`frame.py`): 試験取り込みで、額縁や撮影の黒い余白が写り、地平線の推定が額縁の縁に引っ張られ、SAM が額縁の帯を「物体」として切り抜いたため追加した。(1) 画像の端につながった、ほぼ黒・ほぼ白、または平らで暗い/明るい領域を余白とし、残りの外接矩形に切る。アーチ形の絵の四隅は余白マスクとして残す。(2) 矩形の各辺で、端から続く「辺全体にわたる勾配の層」(Lab の色差。多重の縁取りは隙間 1% まで同じ額縁とみなす)の最も内側の手前まで削る。内容が画像の 25% 未満になるなど不自然なときは、何も削らない。元画像は額縁つきのまま `originals/` に残し、切り出した範囲は `images.crop_box` に記録する。
  - **確認**: 実画像 21 枚で、検出した箱を目視した。額縁(金・木)、黒/灰/白の余白、アーチ形の絵で、箱が絵の内側の縁に沿った。試行の途中で2回後退し(暗い絵を余白と誤認、額縁を削れない)、実画像を見て直した。
  - **限界**: 質感のある暗い縁(met-438849 の上端のキャンバス地の織り目)は残る。絵が台に載った写真(met-436451 の下端)の台は残る。絵と余白が連続する絵(暗い絵で、端が余白と同じ暗さで平ら)は、削りすぎる可能性があるが、今回の21枚には現れなかった。
- **属性判定は取り込みと別の工程**(`judge`): 1 切り抜きにつき 1 回の `ask` に 7 問をまとめる。呼び出しごとの消費を積算して、`--max-neurons` で止まり、次回は続きから再開する。判定の版は「モデルID + 質問の版」で、変わると再判定の対象になる。
- **CPU での速度**(この環境は 4 コア・16 GB。2026-10-31 実測): SAM ViT-B の自動マスク生成は、約 600×480 の画像で 16×16 の格子が約 30 秒、32×32 が約 90 秒。2048 ピクセルの作業用画像では、SAM が 31〜49 秒、指標が 1〜18 秒で、1 枚あたり約 45 秒(21 枚で約 16 分)。CLIP の埋め込みは 1 枚 0.04 秒。約 200 枚を 16×16 で処理すると約 2.6 時間。GPU があれば大きく短縮できる。

### 試験取り込みの結果(2026-10-31、Met の絵画 21 枚。風景 10・馬 3・犬 2・船 2・牛 2・樹木 2)

- **件数**: 切り抜き 183 個(1 枚あたり平均 8.7、最小 1、最大 12)。指標の中央値: 面積比 0.011、`aspect` 1.9(最大 7.9)、`edge_score` 0.86、`clutter` 26(最大 192)。端に接する切り抜きは 43 個、面積比 0.1 超は 20 個(大きな空の断片が中心)。
- **目視(切り抜きの一覧)**: 馬・犬・顔・手・服・木が、きれいに切れたものがある。一方、**植え込みや岩の暗いかたまり、空のちぎれた断片が多い**。絵画の筆致では、SAM が「物体」より「色の塊」を切りやすい。馬群や人混みの絵は、脚だけなど断片になる。額縁の帯は出なくなった。
- **地平線の初期値**: 風景の約半数は妥当に見える(met-435684、436229、436441、436832、437519 など)。当たっていないものもある(met-435702 は y=0.86、met-436593 は低すぎる)。**確信度は当たり外れと対応しない**(外れたものにも 0.7 以上が出る)。正解の地平線を手で付けていないので、誤差は数値化していない。
- **属性判定(Clef-flash、40 個、122.7 ニューロン = 1 個あたり約 3.1)**: 質問 7 問を 1 回にまとめ、画像は灰色の背景に載せた切り抜き(長辺 512 以下)。
  - `watermark_text` はすべて低い(0.01〜0.02)。`cut_off` は、端に接する切り抜きで高い(0.6〜0.8)傾向。`single_object` は、馬・犬・木の塊で高く(0.7〜0.9)、空の断片・顔だけの切り抜きで低い(0.2〜0.3)傾向。ただし植え込みの塊も 0.85 と高く、「物体」と「色の塊」は区別できていない。
  - `facing` は、対象がはっきりしたもの(犬・顔: 正面 0.93、馬: 右 0.88)で確からしい。`light_dir` は、絵画では拡散した光が多く、多くが「不明」で確率も低い(最大 0.55)。
  - これは目視の印象で、**自分の判断との一致率は測っていない**(M1 のゲートは未達)。
- **AI(Haiku)による印付け(2026-10-31)**: 人の印を待たずに、Haiku に同じ一覧を見せて「使える/使えない」を付けさせた(判定の基準は私が書いたもので、あなたの基準ではない)。人の印(`usable`)とは別の列(`usable_ai`、地平線は `horizon_ai_y` / `horizon_ai_na`)に保存し、混ぜない。`scripts/pool.py compare` が、人の印と AI の印の一致(一致率・κ・適合率・再現率)を測る。
  - **結果**: 183 個のうち 84 個(46%)が「使える」。シートごとの割合は 0%(最後の3個)〜63%(91〜120)でばらつく。
  - **再現性**: 同じ一覧(1〜30 と 91〜120 の 60 個)を、もう一度 Haiku に判定させた。一致率 88%、κ = 0.77。ひっくり返ったのは境界の7個(服・顔・縁の欠けた塊など)で、2回目のほうが厳しい傾向だった。**したがって、Haiku を正解にした測定には、少なくとも 12% 前後の揺れがある。**
  - **AI の印を正解にしたときの、自動の指標との関係**: 最も効くのは Clef の `single_object`(AUC 0.68)。次いで端への接触(`border_touch`、少ないほど使える。AUC 0.37 = 逆向きに 0.63)と Clef の `edge_quality`(0.62)。**面積比・マスクの品質・細さはほぼ無関係**(AUC 0.47〜0.48)。`single_object` > 0.5 で「使える」と予想すると、正解率は 0.60(全部を多数派にする場合は 0.54)。適合率は 0.54 で、使えないものを 62 個「使える」と誤る。つまり**機械的な指標だけでは足切りの役に立たず、Clef の判定も強くはない**。ただし、正解が AI の印であり、標本も 183 個と小さいので、傾向の目安にとどまる。
  - **地平線**: AI は 21 枚のうち、直す 2 枚(#2: 0.86→0.35、#14: 0.85→0.40)と対象外 5 枚だけを挙げ、残りは自動の値を受け入れた。**受け入れた 14 枚は誤差が 0 として数えられるので、この「誤差」は精度の根拠にならない**(直した 2 枚の分だけで平均 0.06)。#14 は静物画で、対象外にすべきだった可能性がある。
- **あなたの印(切り抜き 1〜30、30 個。2026-10-31)**: 「使える」は 9 個(7・13 = 木、14・21 = 馬、23 = スカート、25・27 = 手、29 = 顔、30 = 犬)。取り込み済み(`usable`)。**この印の意味は「単体でそのまま使える」**(次の「反復素材」の指摘を参照)。
  - **Haiku との一致**(30 個): 1 回目の判定で一致率 73%、κ 0.44(適合率 0.54、再現率 0.78)。再判定で 80%、κ 0.60。差が出たのは、Haiku だけが「使える」としたもの(9 = 植え込み、15 = 馬の後ろ足だけ、22・24・26・28 = 布)。**私が書いた基準が「布」を使える例に挙げていたことが、原因の一部**。Haiku を代用するなら、基準をあなたの印に合わせて書き直し、もう一度一致を測る必要がある。
  - **自動の指標**(30 個。3 枚の絵から、使える 9 個): あなたの印とよく対応したのは `thickness`(AUC 0.88)、`clutter`(0.87)、`area_ratio`(0.83) = **大きく太い物ほど使える**。Haiku の印では、面積・細さはほぼ無関係(0.47〜0.46)だった。Clef の `single_object` > 0.5 は正解率 0.47(全部「使えない」にした場合の 0.70 より低い)。標本が小さく、AUC の誤差は ±0.09 程度(Hanley-McNeil の式による概算)。傾向の目安にとどまる。
  - **足切りへの示唆**: 小さな塊(面積比 0.004〜0.01)が大量に出るが、あなたの印では「使える」がほとんどない。面積と太さによる足切りは効きそうだが、M2 で、より多くの印を取ってから決める。
- **反復素材(リピート)の指摘(2026-10-31、印は「独立した2つ」に決定)**: コラージュの素材は、単体の物として成立していなくてもよく、**同じ切り抜きを繰り返し並べれば使える**(繁み・雲・布・群衆など)。単体で使えるものも反復に使える(馬を並べて群れにする、など)。そこで印を、**独立した2つ**にする: `usable` = 単体でそのまま使える、`repeat` = 反復して使える。組み合わせで役割が決まる: 両方 / 単体だけ / 反復だけ / 使えない。(初めは排他的な3段階にしたが、あなたが 21(馬)を両方に挙げたので、独立した2つに改めた。)`scripts/pool.py import-labels --usable … --repeat … --upto N` で取り込み、`eval` / `compare` が集計する(AI の印は `usable_ai` / `repeat_ai`)。
  - **あなたの印(1〜30)**: 両方 1 個(21)、単体だけ 8 個、反復だけ 6 個(1・6・12・15・26・28)、使えない 15 個。半分(15 個)は何かに使える。
  - **足切りの手がかり(30 個。3 枚の絵だけで、閾値は同じデータを見て選んだので、確かめ直しが要る)**: 役割ごとの面積比の中央値は、単体 0.031、反復 0.012、使えない 0.006。面積比 ≥ 0.008 で足切りすると、**単体・反復はすべて残り(再現 1.00)、使えないものの 60% を落とせる**(30 個中 21 個が残る)。≥ 0.010 では、単体は全部残るが、反復の 2 個を失う(再現 0.87)。単体か反復で使えるかの予測では、`clutter`(AUC 0.91)、`thickness`(0.89)、`area_ratio`(0.84)がよく効く。反復だけの予測は弱く(`clutter` 0.67、`thickness` 0.66、`area_ratio` 0.62)、反復素材は機械的な指標だけでは見分けにくい。
  - 設計への影響(未決): 配置で、反復素材は「範囲を指定して敷き詰める」処理が要る(R5 の遠近でサイズを変えながら並べる)。要素分解(背景 / 主役 / 小物)に「反復」の役割を加えるか。足切りも、単体用と反復用で分ける必要がある。
- **Claude による印付け(2026-10-31、切り抜き 31〜183 の 153 個)**: あなたの提案で、私(この作業をしているモデル)が付けた。人の印・Haiku の印とは別の列(`usable_claude` / `repeat_claude`)に保存。
  - **基準は、あなたの 1〜30 の印からの推測**(あなたが言葉で基準を述べたわけではない)。単体 = 馬・犬・牛などの動物、樹形のある木、顔・手、建物、ボート、一つの物として成立する小物。反復 = 空・雲の断片、布。茂みや岩の暗い塊は、どちらでもない。反復は、単体の物にはほとんど付けない(あなたの印では 21 の馬だけが両方)。1〜30 は、あなたの印を見ているので、私の印を付けていない。
  - **結果**: 単体 36 個(24%)、反復 23 個(15%)、使えない 95 個(両方 1 個)。迷ったもの(単体: 57・58・95・109・111・113・125・140・148・160・163、反復: 33・34・37・96・98・111・119)は、印は付けたが不確か。
  - **自動の指標は、あなたの 30 個とは違う姿になった**: 「単体で使える」に対する `area_ratio` の AUC は 0.57(あなたの 30 個では 0.83)。私の単体には小さなボート・円柱・小物が多く、あなたの 30 個は大きな馬・犬が中心だった。**足切りの閾値は標本の偏りに敏感で、まだ決められない**。一方「反復して使える」には `area_ratio`(0.83)・`thickness`(0.81)・`mask_quality`(0.78)が効く(大きな空の断片が多いため)。Clef の `single_object` は AUC 0.68 だが、「> 0.5 なら使える」の予想は正解率 0.41(全部を「使えない」にした場合の 0.77 より低い)。
  - **抜き取り確認(あなたの印 24 個、私の印は伏せて取った。2026-10-31)**: 単体で使える: 一致率 88%(κ 0.71、適合率 0.75、再現率 0.86)。反復して使える: 一致率 92%(κ 0.70、適合率 0.60、再現率 1.00)。4 役割(両方 / 単体 / 反復 / 使えない)の完全一致は 19/24 = 79%(95% 区間は約 0.60〜0.91)。食い違った 5 個: 37・151(私が反復、あなたは使えない)、80(廃墟の塔)・174(横たわった長靴)(私が単体、あなたは使えない)、107(ベージュの板状の布)(あなたが単体、私は使えない)。**私は、あなたよりやや甘く付ける傾向**がある。24 個なので幅は広く、目安にとどまる。Haiku の印との比較(あなたの 30 個で κ 0.44〜0.60)は、標本も基準も違うので、厳密には比べられない。
  - **あなたの印が 54 個になったので、評価を取り直した**(単体 16 個、反復 9 個、両方 1 個を含む。使えない 29 個): 「単体で使える」の予測で効くのは Clef の `single_object`(AUC 0.71)、`thickness`(0.70)、`area_ratio`(0.69)、`clutter`(0.68)。「単体か反復で使える」には `thickness`(0.82)、`clutter`(0.80)、`area_ratio`(0.79)が効く。**ただし Clef の `single_object` > 0.5 で「単体で使える」と予想した正解率は 0.52 で、全部を「使えない」にした場合の 0.70 を下回る**(適合率 0.36、再現率 0.81)。
  - **M1 のゲートの現状**: 「属性判定とあなたの判断の一致率 80% 以上」は、「単体で使えるか」の判定では **未達**(Clef で 52%)。cut_off・向き・光の方向など、ほかの属性には、あなたの印がまだない。私の印は、あなたと 88% 一致した(未達の代わりに使える水準)。
- **CLIP-CLOP の patch maker 相当(Mask R-CNN)の試験(2026-10-31)**: Arnheim 3 の patch maker は、PixelLib の Mask R-CNN(COCO)で検出した物体ごとに切り出す(TensorFlow 2.0.1 が要る古い実装で、この環境では動かない)。同じ種類のモデルを、torchvision の Mask R-CNN(ResNet50-FPN v2、COCO の重み)で代用し、同じ 21 枚(作業用画像)で試した。重みのライセンスは未確認。
  - **速度**: 1 枚あたり平均 4.3 秒(SAM は約 45 秒)。スコア 0.5 以上の検出は 238 個(人 121、ボート 38、馬 30、牛 20、鳥 7、犬 6、…)。
  - **良い点**: SAM が出さなかった**ボート(きれいに切れる)・立った人物(全身)・小さな人物(風景のスケール感に要る)・馬の全身**が、クラス名つきで出る。
  - **弱い点**: (1) COCO に**木・雲・山・建物・手・顔だけ**といった分類がない。あなたが「単体で使える」とした 9 個のうち、検出と一致(IoU ≥ 0.5)したのは 3 個(馬 2・犬)で、残り 6 個(木 2・スカート・手 2・顔)は検出されない。 (2) 風景画で**誤検出**が出る(met-436441 の植え込みが「cow 0.96」「zebra 0.93」「elephant 0.61」)。検出スコアでは見分けられない。 (3) 馬群・人混みの絵では、脚だけ・体の一部の断片になる。
  - **CLIP による誤検出の除去は、単純な方法では効かなかった**: 80 クラスのゼロショット(「a painting of a {クラス}」の確率)で、誤検出(436441 の 6 個)の 4 個は除けたが、確かな検出(score ≥ 0.8 の 46 個)も 35 個失う(閾値 0.2)。小さな切り抜きや全身像で確率が低く出るため。誤検出の「cow 0.94」には CLIP 確率 0.83 が出て、逆に通ってしまう。Clef の「これは {ラベル} か」(noul)は、未試験。
  - **位置づけ(案)**: SAM の代わりにはならない(あなたの単体 9 個のうち 7 個は SAM だけが出した)。**SAM を残したまま、候補を足す第二の経路**としては有望(ボート・人物・動物)。ただし、誤検出を除く方法が要る。
- **このあと**: M1 のゲート(属性判定と自分の判断の一致率 80% 以上)を測るには、正解の付け方が要る。地平線は、コンタクトシートを見て `scripts/pool.py set-horizon` で直せる。切り抜きの良し悪しも、一覧を見て印を付ける方法が要る。

## ClefとClairicの使い方

Clefは選択と採点を担当する判定モデル、Clairicは数値を出す抽出モデルとして分担する。どちらも文章を生成せず、確率や型付きの値だけを返す。

確認済みの仕様:

- Clef: 質問の型は3種類。`noul`(はいの確率)、`choice`(選択肢ごとの確率と確信度)、`score`(順序付きの評価基準での確率重み付きスコアと各段階の確率)。1リクエストで最大 64 問。状態と一緒に最大4枚の画像を渡せる。
- Clairic: テキストと最大4枚の画像から、名前と型を指定した項目(数値・日付・リスト・推定値)を埋め、各項目に確信度か80%範囲が付く。2026-10-19公開のプレビュー。
- 呼び出し: Workers AIの REST API。トークンはWorkers AIのReadとEditが必要。PythonからはRESTで呼ぶ。
- **リクエスト形式(2026-10-31 に公式ドキュメントで確認し、合成データで実際に呼んで裏取り。`adapters/cloudflare.py` に実装済み)**:
  - `POST https://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/ai/run/@cf/cloudflare/{clef|clef-flash|clairic}`、`Authorization: Bearer <token>`。応答は `{"result": {...}, "success", "errors": [{"code","message"}], "messages"}` に包まれる。
  - Clef の body: `model`("clef" か "clef-flash")、`state`(**必須**。文字列か JSON。空文字は可で、省略すると 400)、`questions`(1〜64問。id は英数字と `_ . -` の100文字まで)、`images`(最大4枚)。質問は `noul`(`instructions`)、`choice`(`criteria` = 選択肢 id → 説明 or null。2〜255個)、`score`(`criteria` = 低い順の説明の配列。2〜10段階)。
  - Clef の答え: `noul` → `{noul}`、`choice` → `{choice, probabilities, confidence}`、`score` → `{score, legend, probabilities, confidence}`。**score は 0 始まり**(最低段階 = 0。段階の間の値になる)。`probabilities` のキーは choice では選択肢 id、score では段階の番号の文字列。
  - Clairic の body: `model`、`state`(文字列。画像があれば空でよい)、`fields`(項目名 → `type` と指定)、`images`(最大4枚)。型は text / number / date / time / datetime / duration / list / estimate / forecast。**estimate は `min` と `max` が必須**(`step`、`scale: "log"` も指定できる)で、`{value, mean, median, p10, p90, p_below, p_above}` を返す。p10〜p90 が設計書の「80%範囲」にあたる。入力から決まらない項目は `value: null`。
  - 画像: base64 埋め込み(`{content_type, base64}` か data URL)のみ。PNG / JPEG / WebP、1枚 4 MiB・16 メガピクセルまで、合計 8 MiB まで。URL は不可。
  - 画像のトークン数: 各辺を 32 の倍数に丸め、面積が約 65,000 px(256×256)未満なら拡大、約 1 メガピクセル超なら縮小。32×32 ごとに 1 トークン、1枚の上限 1,024 トークン。64×64 の画像は 256×256 に拡大され、64 トークン(実測)。
  - 消費ニューロンは応答ヘッダ `cf-ai-neurons` に入る(本文の `usage` はトークン数のみ)。Clef は出力トークンを課金しない。
  - エラー: 3036 (429) = 1日の無料枠を使い切った、3040 (429) = 一時的な容量不足、5006 (400) = 入力の形が不正(実測)、3006 (413) = 大きすぎる。

用途と質問設計(案):

| 用途 | モデル | 型 | 質問の例 | いつ |
| --- | --- | --- | --- | --- |
| 検索語との一致の確認 | Clef | noul | この切り抜きは「犬」か(検索後の上位候補だけ) | 実行時 |
| 見切れ | Clef | noul | 主役が画面端で切れているか | 事前 |
| 透かし・文字 | Clef | noul | 透かしや文字が入っているか | 事前 |
| 向き | Clef | choice | 正面 / 左 / 右 / 後ろ / 不明 | 事前 |
| 光の方向 | Clef | choice | 左 / 右 / 上 / 正面 / 不明(素材と背景の両方) | 事前・実行時 |
| スタイル | Clef | choice | 洋画 / 日本画 / イラスト / 写真 | 事前 |
| 切り抜きの縁 | Clef | score | 縁のきれいさ 1–5 | 事前 |
| 位置・大きさ・回転 | Clairic | 数値項目 | x, y, z(手前–奥), scale, rotation + 80%範囲 | 実行時 |
| 合成結果の自然さ | Clef | score | 光・大きさ・向きの自然さ 1–5 | 実行時 |

呼び出し予算の方針(案):

- 無料枠は全モデル共通の1日10,000ニューロン(00:00 UTCリセット)。**実測と公式の料金表(2026-10-31)**:
  - Clef: 21,818 ニューロン/M 入力トークン($0.24/M)。Clef-flash: 3,455(約6分の1)。Clairic: 9,091($0.10/M)。
  - 実測: Clef 326 トークンで 7.11、64×64 画像1枚+質問1問(210 トークン)で 4.58。Clairic 325 トークンで 2.95、226 トークンで 2.05。料金表の単価と一致した。
  - 目安: 326 トークンの Clef 呼び出しなら、1日に約1,400回。M1 の約200枚を、画像1枚 + 質問10問ほど(約1,300トークン、約28ニューロン)で判定すると、約5,700ニューロンで、1日の無料枠に収まる見込み(質問数に依存)。
  - 未確認: プレビューの Clairic の消費が1日の無料枠に数えられるか(ヘッダには消費が出る。ダッシュボードで確認する)。
  - レート制限: Text Generation の区分は 300 リクエスト/分(制限のページ。Clef がこの区分かは推定)。
  - 公式の速度: Clef の遅延は中央値 209 ms、Clef-flash は 38.8 ms。実測した往復は 0.4〜1.1 秒。
- 結果は(画像ハッシュ, 質問セットとモデルの版)をキーにキャッシュする。事前判定は最初の1回だけ。
- 1リクエストに質問をまとめる(最大 64 問)。実行時の遅延重視の箇所はClef-flashを検討するが、画像入力に対応するかは未確認。
- 枠を超えたときは、CLIPのスコアと機械的指標だけで動く縮退モードに落とす。

実装の境界(案): `Judge`(選択・採点)と `Estimator`(数値推定)の2つのインターフェースを切り、最初はCloudflareのREST実装で埋める。Clefの重みはApache 2.0でHugging Faceにあるため、将来ローカル実装に差し替えられる。

実装の境界(2026-10-31 作り直し。`adapters/` に実装済み):

- `Judge.ask(questions, images, state)` は、質問を**まとめて**受けて、渡した順の結果と使用量(`Usage`: API 呼び出し数・キャッシュ命中数・ニューロン消費・遅延)を返す。上限(質問数・画像数)は抽象側でなく、実装ごとの `capabilities` が持つ(Clef は 64 問・4 枚)。上限を超える質問数は `ask_in_chunks` が分けて送る。
- 結果の型は `NoulResult` / `ChoiceResult` / `ScoreResult`。すべて `question_id` と `cached` を持つ。
- キャッシュは `CachedJudge`(SQLite)。キー = (画像のハッシュ, 正規化した質問, model_id, state)。質問の `id` はキーに入れない。命中しない質問だけを中身に尋ねる。失敗はキャッシュしない。
- 失敗は例外(`InvalidRequest` / `BudgetExceeded` / `RateLimited` / `ApiError`)で返す。縮退モードは設けないので、握りつぶして代わりの値を返さない。
- `Estimator.estimate(text, fields, images)` は、項目に型・単位・範囲(`EstimateField`)を持たせ、値と確信度・80%範囲(`EstimateValue`)を返す。
- `FakeJudge` が外部通信なしで Clef と同じ上限の検査をする。テストと、パイプライン側の開発に使う。
- 解決済み(2026-10-31): `state` は文字列か JSON(空文字可)。`ScoreResult.score` は 0 始まり(5段階なら 0〜4)で、質問の「縁のきれいさ 1–5」は 5段階の説明を渡し、結果を 0〜4 として扱う。
- 未決: 透明部分のある切り抜きを何色で埋めて渡すか(PNG のまま渡したときの Clef の見え方は未検証)。
- 「ローカル CLIP に差し替えられる」は、`Judge`(質問に答える形)の単位では成り立たない。差し替えは、工程単位(配置・属性付け・採点)のインターフェースを切ったうえで行う(次の作業)。

## パッチ選択

Sketch2Photoの「フィルタで候補を絞り、組み合わせに点を付けて最良を選ぶ」挙動を、事前計算した指標と属性で再現する。以下の数値はすべて初期値の案で、M2で素材を見て調整する。

1. 要素分解: 文章を要素のリスト(名前、役割=背景/主役/小物、検索語、プール)に分ける。Clairicのリスト項目でできるかを検証し、難しければ規則か別のモデルにする。
2. 検索: 要素ごとに、指定プールの索引からCLIP類似度の上位K件(K=50)を取る。
3. 機械的な足切り: DBの指標で落とす。主役マスクの面積比が極端に小さい/大きいもの、中心から遠いもの、マスク数が多い(ごちゃつき)もの、解像度が配置サイズに対して不足するもの、縁スコアが低いもの。
4. 属性フィルタ: Clefの属性でさらに落とす。主役確率が低い、見切れ確率が高い、透かし・文字の確率が高いもの。
5. 単体スコア: unary = CLIP類似度、縁スコア、主役確率の重み和。要素ごとに上位M件(M=5)を残す。
6. 組み合わせ選択: 要素数は6程度を上限とし、候補の組をビーム探索(幅B=10)で選ぶ。合計点 = 単体スコアの和 + 素材同士の相性の和。相性は光の方向の一致(choiceの確率ベクトル同士の積)、色分布の距離(切り抜きの元画像と土台の Lab ヒストグラムの χ² 距離。Photo Clip Art に倣う)、スタイルの一致、スケールの整合。背景画像がある場合は背景の光との一致を優先する。
7. 左右反転の救済: 光の方向が逆で、反転しても不自然でない物体(Clefのnoulで「左右反転して不自然か」を事前判定)は、反転して再評価する。
8. 出力: 上位N組(N=3)を合成に渡す。選ばれなかった候補は、再試行用に保持する。

Sketch2Photoのフィルタ基準(2026-10-31 に論文本文で確認):

- 顕著領域を求め、その周囲の幅30ピクセルの帯の中のセグメント数を数える。10を超える画像は「複雑すぎる」として捨てる。対象は背景が単純な画像に絞られる。
- 物体の切り出しは、顕著領域を膨張させて GrabCut をかけ、境界が変わらなくなるまで(最大20回)繰り返す。こちらでは SAM に置き換える。
- 風景の背景は、検索結果の約1000枚から内容の一致で100枚に絞り、地平線がキャンバスと30%(画像の高さに対して)以上ずれたものを捨てたあと、均一な領域が大きいものを上位20枚残す。
- 帯の幅30ピクセルは画像サイズに依存する。論文の画像サイズは確認していないので、こちらでは画像サイズに対する比で持つ。数値(10個など)は初期案として使い、M2で素材を見て調整する。

## 配置・切り抜き・合成

選ばれた素材の組を、位置推定→変形→重ね順→なじませの順でキャンバスに載せる。ここから先は画素を扱うため、Clef/Clairicは判断と数値のみを担当し、実際の変形と合成は通常の画像処理で行う。

1. 位置推定: Clairicに要素ごとの x, y(足元), scale(倍率), rotation, 実寸の高さを数値項目として尋ねる(z は規則で決める。「風景ルール」R10 参照)。入力は文章と背景画像(あれば)。各値に付く確信度か80%範囲を保存する。
2. 粗→精の絞り込み: 80%範囲が広い項目は、候補領域を切り出してもう一度尋ねる(最大2回を案とする)。それでも広いときは、格子分割の候補をClefの採点で選ぶ。
3. 変形: scaleとrotationを素材の切り抜きPNGにアフィン変換で適用し、必要なら左右反転する。
4. 重ね順: zの順位で奥から手前へ重ねる。奥行きのある場面では、単眼の深度推定モデルで背景の深度を出して補助とする。
5. なじませ: スタイルプールごとに方式を切り替える。絵画・イラスト系は縁の羽根ぼかしとアルファ合成を基本にする(継ぎ目が見えても作風として成立しやすい)。写実プールはポアソン合成(OpenCVのseamlessClone)と影の追加を基本にする。
6. 挿入モデル(任意、後続フェーズ): 写実プールで継ぎ目や影が気になるときに、Paint by Exampleのような参照画像付きインペインティングを使う。ライセンスと顔の非対応が制約になる(「ベース実装」参照)。

座標の規約(案): x, y はキャンバス幅・高さを 0–1 に正規化した値、z は整数の順位、rotation は度(時計回り)とする。Clairicへの問い合わせでもこの規約を明示する。

Clairicが画像から「置くのに自然な位置」をどこまで正確に推定できるかは未検証。M3の最初の実験で確かめ、低い場合の代替案として、格子候補をClefの採点で選ぶ方式を用意する。

## 評価と再試行ループ

Sketch2Photoが合成結果に数値の点を付けて最適な組み合わせを探した考え方を、複数の評価軸の重み和で再現する。

評価軸(案):

| 軸 | 計算 | 役割 |
| --- | --- | --- |
| 意味の一致 | 合成画像と要望文のCLIP類似度 | 要望から外れていないか(物の有無・作風に限る。位置関係は測れない前提で、規則 R4〜R8 の検査と目視で見る) |
| 自然さ | Clefのscore(光・大きさ・向きの自然さ 1–5) | 継ぎ目や違和感の検出 |
| 一貫性 | 素材間の色味・スタイル・光の距離 | トーンのばらつき |
| 縁の品質 | 合成後の境界帯のエッジ指標 | 切り抜きの粗さ |

ループ(案):

1. パッチ選択の上位3組をそれぞれ合成して点数を出す。
2. 合計点が閾値以上のものがあれば、最高点を採用して終了。
3. なければ、自然さスコアが低い原因の要素(点数の分解で特定)を候補の次点と入れ替えて再合成する。
4. 再試行は最大3回。超えたときは、最高点の候補を「要確認」として返す。

ログ: すべての試行について、採用素材、変形パラメータ、各軸の点数、呼び出し回数をJSONで保存する。重みや閾値の調整はこのログと目視を突き合わせて行う。

重みや閾値は初期値を決めていない。M4で、人が「良い」と判断する結果と点数がよく相関するように調整する。

## 検証計画とマイルストーン

各段階に「次へ進む条件(ゲート)」を置く。ゲートの数値はすべて初期の案で、結果を見て見直す。

1. M0 環境と基準: リポジトリ構成(案: `pipeline/` `adapters/` `data/` `scripts/`)、設定ファイル、Judge/Estimatorのインターフェースを作る。Colabで Arnheim 3 をサンプルパッチで動かし、基準の出力と速度を記録する。ClefとClairicの1回あたりの消費ニューロンを実測する。ゲート: ClefとClairicをRESTで呼び、画像1枚に対する結果をログに残せる。(2026-10-31 に合成データで達成。`scripts/m0_probe.py` がログを `data/logs/` に残す。Colab での Arnheim 3 の実行は未実施。)
2. M1 素材プール: 1プール(例: 美術館のオープンアクセス絵画)約200枚を取り込み、埋め込み、SAM切り抜き、Clef属性判定、DB登録を行う。ゲート: 目視で切り抜きの良し悪しを確認し、属性判定と自分の判断がどの程度一致するかを数値化する(一致率の目安 80%以上を案)。
3. M2 パッチ選択: 要素分解、検索、足切り、組み合わせ選択を実装し、要望文ごとに上位候補を一覧(コンタクトシート)で確認できるようにする。ゲート: 10件の要望で、上位3組のうち少なくとも1組が自分から見て「使える」。
4. M3 配置と合成: 最初に位置推定の検証実験を行う。位置が既知の合成画像(物体を決めた座標に貼ったもの)を数十枚作り、Clairicの推定値と真の座標の相関(Spearman)と誤差を見る。相関が低ければ、格子候補をClefで選ぶ方式に切り替える。その後、変形・重ね順・なじませを実装する。ゲート: 相関の目安 0.7以上を案とするか、代替方式で同等の精度が出ること。
5. M4 評価ループ: スコアと再試行を実装し、ログと目視を突き合わせて重みを調整する。ゲート: 再試行なしの結果より、ありの結果の方が自分から見て改善していること。
6. M5 拡張: スタイル別プールを増やす、素材がない要素の生成フォールバック、CLIP-CLOPによる細部の最適化、Paint by Exampleによる縁の仕上げ、部品差し替えUI。ゲート: フェーズごとに個別に決める。

## 設計レビューの論点(未反映・未決)

2026-10-31 に別モデルで批判的にレビューした結果。**本文にはまだ反映していない。** どれを採用するかは決めていない。レビューは設計書と骨組みの読解に基づき、外部仕様は確認していない。

主な問題:

1. **配置の検証が本番の課題とずれている。** M3の実験は「貼った座標を当てる」で、本番の「まだ置いていない物体の置き場所を提案する」とは別の課題。配置の入力に選んだ素材の形が入っていない。パッチ選択が配置サイズより前に「配置サイズ」で足切りしており、順序が矛盾している。不確実性が最大なのに検証が M1・M2 の後。
2. **素材の網羅性が薄い。** 約200枚のプールで K=50 なら検索が絞り込みにならない。埋め込みは元画像全体、貼るのは主役マスク1つで、検索の対象と貼る対象がずれる。「主役は『犬』か」は、取り込み時に要望文が分からないので事前判定にできない。
3. **成功基準と評価指標が未確定。** 「意味の一致」が検索と同じCLIP類似度の繰り返し。Clefの自然さ判定の精度が未確認事項の表にない。再試行の「原因要素の特定」の方法が未定で、差し替えるのは素材だけ(配置は見直さない)。ゲートが主観のみ。

その他の指摘:

- ビーム探索は不要(M=5、要素6つで 5^6 = 15,625 通り)。それより上位3組が似た組になる問題への対策が要る。
- 欠けている部品: 色合わせの補正、背景の作り方、キャンバス定義、座標規約(中心か接地点か)、深度推定モデルの計画、顔除外の仕組み。
- 縮退モードでは配置ができない。1回の実行での呼び出し回数の見積もりがない。
- 規則ベース配置(役割別テンプレート)を基準かつ縮退モードにする案。
- 重み和の前に正規化が要る。閾値での終了は較正なしでは機能しない。
- M1の一致率80%は偏りのある属性では甘い(適合率・再現率で測る)。M3のSpearmanは位置の指標として不適切。
- 骨組みの `Judge` は1問ずつしか聞けず、64問まとめ送信ができない。結果にモデルの版・消費量が付かない。予算超過の例外がない。工程単位(`Placer` / `Tagger` / `Critic`)に切る案。
- (後回し中の権利)NDの素材は除外が必要、BY / BY-SA の出力物側の義務、外部AIへの送信可否。

マイルストーン並べ替えの案(未決):

1. M0: API調査(形式・消費量・上限)と、成功基準・ベンチマーク用要望文(20件程度)の固定。Arnheim の実行は M5 へ。
2. M0.5: Clef/Clairic を使わない最小の通し実装(手で選んだ切り抜き、切り抜き単位のCLIP検索、規則ベース配置、アルファ合成)。基準かつ縮退モード。
3. 配置方式の比較実験を、本番に近い課題で行う(実写から物体を除いて元の位置を当てさせる、など)。
4. 素材の網羅性の確認(要望の各要素について、使える切り抜きが上位K件に入る率)。
5. 属性判定、パッチ選択、評価指標の検証と評価ループ、拡張。
