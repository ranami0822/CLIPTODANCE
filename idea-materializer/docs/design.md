# 設計メモ(アイデア具現化マシーン)

2026-10-31 時点。**実測は小さな 1 つのサンプル(素材 3 個・丸/三角/四角のスケッチ)だけ**で、一般的な精度はまだ分からない。

## 目的

- 軽いスケッチ(丸や三角の粗い絵)と、手元の素材(画像・透過 PNG)と、ひとことのテーマから、素材を**動かして並べた**構図を出す。
- 絵は生成しない。素材を回し、x・y・z に動かして、人が最後に手で直す。
- 本筋(テキストから検索した画像の切り抜きでコラージュを作る)とは別物。本筋は素材を検索で集めるが、こちらは**素材を人が持ち込む**。

## 用語の確認(出どころ)

- **Clairic**: Cloudflare Workers AI の抽出モデル(2026-10-19 公開のプレビュー)。テキストと最大 4 枚の画像から、名前と型を指定した項目を埋め、各項目に確信度か 80% 範囲が付く。出どころは本筋の `docs/design.md`。
- **Clef**: 同じく Cloudflare の判定モデル。選択(choice)・はい/いいえ・採点を確率で返す。出どころは同上。
- **Sketch2Photo**: 依頼の「skectchToPhoto」は、本筋の設計書が参考にしている Sketch2Photo(Chen ら 2009)のことと読んだ(推測。違っていたら教えてほしい)。

## 流れ

1. **素材の取り込み**(`imaging.prepare_object`): 透過があればそのまま。なければ縁の色を背景として、縁につながる領域だけを抜く。縁の色が一様でなければ失敗として知らせる(無理に抜かない)。
2. **スケッチの塊の検出**(`imaging.sketch_regions`): 線を粗い格子にまとめ、近い線をつなげて、つながった塊に分ける。小さな点は捨てる。塊に 1, 2, 3… と(上から下・左から右の順で)番号を振り、青い枠と番号を画像に描く。
3. **対応づけ(Clef)**: 素材ごとに「どの塊に当たるか」を選択問題(選択肢 = 各塊 + 「当たらない」)で聞き、確率を得る。塊を重複して使わない、確率の積が最大の割り当てを全探索で解く(`arrange.solve_assignment`)。
4. **推定(Clairic)**: 素材ごとに z(奥行き)・rot(傾き)・x・y・scale を、80% 範囲つきで出す。state には、手順 3 の結果と、素材名・テーマを文で渡す。画像はスケッチ(枠つき)と素材のコンタクトシート(A, B, C… の札つき)の 2 枚。
5. **規則で決める**(`arrange.apply_regions` / `postprocess`):
   - 塊に対応した素材は、x・y を塊の中心、大きさを「素材の外接矩形が塊の矩形に収まる最大」にする。Clairic の x・y・scale は使わない。
   - 塊に対応しない素材は、Clairic の x・y・scale をそのまま使う。
   - 中心をキャンバス内に収め、範囲外の値を丸め、**補正した事実を画面に出す**。
   - 回転の 80% 範囲が 60° より広ければ、根拠がないとみて 0° に戻す(下の「実測」参照。閾値は仮置き)。
   - 描く順は z の小さい順(奥から)。
6. **画面で直す**: ドラッグ・回転・ホイールで拡大縮小・スライダー。PNG と配置 JSON を書き出す。

## 座標の約束

| 項目 | 意味 |
| --- | --- |
| x, y | 素材の中心。キャンバスの幅・高さに対する 0–1。原点は左上 |
| z | 奥行き。0 = いちばん奥、1 = いちばん手前。**今は描く順と、スライダーの値**(3D の奥行きではない) |
| scale | 素材の長辺 ÷ キャンバスの長辺 |
| rot | 度。時計回りが正。0 = 取り込み時の向き |

## 実測(2026-10-31、同じ入力、1〜2 回ずつ)

入力: 素材 = 木・太陽・家、スケッチ = 左下に三角・右上に丸・右寄りに四角、テーマ「夏の朝。左の下に木、右の上に太陽、真ん中より右に家。」。正解は木→三角、太陽→丸、家→四角。

| 方式 | 結果 |
| --- | --- |
| A. Clairic に x・y・scale を直接数字で出させる | 木は約 (0.26, 0.48)(正解の中心は (0.24, 0.62))。太陽は x≈0.71(正解 0.86)で、大きさは 0.47(丸は約 0.13)と大きすぎた。**家は左下 (0.32, 0.69) に置かれ、右寄りの四角と合わなかった**(テーマにも「右」と書いてあった) |
| A'. A に 0.25 刻みの座標グリッドを重ねる | 改善なし(木の y はむしろ悪化 0.25、家は x=0.39 のまま)。グリッドは採用しなかった |
| B. Clairic に「何番の塊か」を数値(estimate)で出させる | 3 素材とも 1 番に寄り、80% 範囲は 0〜2 と広かった(当てずっぽう) |
| **C. Clef の選択問題で対応づけ + 塊の矩形から位置・大きさ(採用)** | 3/3 正解。確率は 木 0.58〜0.74、太陽 0.91〜0.93、家 0.45〜0.55(3 回の実行)。位置・大きさは塊の矩形から決まるのでスケッチと一致 |

読み取れること(推測を含む): Clairic は数値の抽出は得意でも、スケッチ上の位置を数字に直す作業は苦手に見える。選択はClef のほうが向く。役割は本筋の設計書(「Clef は選択と採点、Clairic は数値」)と同じ分担に落ち着いた。

回転: C の Clairic の rot は 3 素材とも 11〜16° で、80% 範囲は 60〜100° 幅だった。値が似通っていて範囲も広いので、根拠のある傾きとは言えないと判断し、範囲が 60° を超えたら 0° に戻す規則を足した(実測 1 サンプルからの仮置き)。傾きの付け方は未解決。

## 参考にした既存研究

下の要約は**本筋の `docs/design.md` の記述による**。この別プロジェクトでは、論文本文を読み直していない。

- **Sketch2Photo**(Chen ら 2009): スケッチと文字ラベルから、ネットで見つけた写真を縫い合わせる。不適切な検索結果をフィルタで除き、合成結果に数値の点を付けて最適な組み合わせを選び、最後に人が対話的に直す。
  - 取り入れた点: 「スケッチ(位置の指定)+ 素材 → 合成 → 人が直す」という全体の形。
  - 違う点: あちらは素材をネットの検索で集め、スケッチの位置は人の指定どおりにする。こちらは**素材を人が持ち込み**、スケッチは粗くてよいので**対応づけと奥行き・傾きを推定する**。合成も、あちらの継ぎ目のない合成ではなく、アルファ合成だけ(縁の羽根ぼかしもまだない)。
- **Photo Clip Art**(Lalonde ら 2007): 地平線と足元の位置から、物の大きさを決める。本筋では R5(サイズ)に使っている。こちらは未採用だが、素材の大きさを z・足元から決めるときの候補。

## 分かっていないこと・限界

- 実測は 1 サンプル。スケッチが複雑なとき(線が互いに触れる、塊が多い、塊の中に別の塊がある)の挙動は未確認。
- 線が近いと、別々のはずの塊が 1 つにまとまる(`merge` を小さくすれば分かれるが、1 つの絵の線が割れやすくなる)。
- z は「描く順」と数値だけ。**本当の 3D の奥行き・3D 回転はしていない**。
- 素材の切り抜きは、単色背景の画像だけ自動。それ以外は透過 PNG を使うか、許容値を手で変える。SAM や rembg は使っていない。
- 合成は、重ねるだけ。光・色・影のなじませはない。
- Clairic はプレビューで、予告なく変わる・止まる可能性がある(公式の利用条件)。回転の 60° の閾値も、モデルが変われば見直す。
- プレビューの Clairic の消費が 1 日の無料枠に数えられるかは未確認(本筋の設計書にも同じ未確認事項がある)。

## 次にやること(候補)

1. 別のスケッチ・素材で、対応づけと位置の当たり具合を数十件測る。
2. 塊の中の傾き(三角の傾きなど)を、塊の形から決める。
3. z をもとに、足元の y と大きさを整合させる(Photo Clip Art 流)か、本当の 3D に出す(three.js など。素材を板として置く)か、方針を決める。
4. 縁の羽根ぼかし・色合わせ。切り抜きの手直し(ブラシ)。
